## Three contracts

TM0 is the text envelope implemented by `decodeMemo` and `validateMemo`.
The marker is exactly `TM0`. A marker of `TM` plus digits, including the
string `TM1`, is `UNSUPPORTED_VERSION`. Any other unexpected marker is
`INVALID_MARKER`. The default maximum is 80 UTF-8 bytes.

TM1 Draft 0.2 is the historical specification in
`docs/protocol/tm1-spec.md` and the wording still present in the
implementation. It defines LOKAD `544d4d00`, version `0x01`, and one active
event, POST `0x01`. The package version and `tm1-test-vectors.json` still
say spec draft `0.2`. Draft 0.2 does not authorize P2SH authorship, and its
candidate rule is the LOKAD prefix.

TM1 Core v1.0 is the contract ratified by the baseline merge. It keeps POST
`0x01` and rejects `REPLY=0x02`. Social version `0x02` stays outside Core.
Ratification section 11 item 2 permits an unrelated `OP_RETURN` beside
exactly one TM1 candidate, and it records that the Tonalli verifier may
also reject a combined TM0 plus TM1 transaction as an
implementation/profile difference. That sentence documents the difference.
It is not a decision that closes S0-07. Section 11 item 7 keeps RFC-0001
outside Core. The Draft 0.2 instruction not to emit production TM1 was
superseded prospectively by that ratification; this suite does not reopen
it and does not activate version `0x02`.

`author_input_index` has two different stages. `parseTm1Output` accepts any
byte 0 through 255 inside a well-formed version `0x01` POST. That acceptance
is structural. `verifyTm1DesignatedInput` then checks the index against the
input list, prevout availability, P2PKH script form, scriptSig shape, HASH160,
and sighash `0x41` or `0xc1`. It returns before any signature digest check.
`VERIFIED_TM1` from `verifyNormalizedTransaction` carries
`trustModel: "trusted-chronik"`. It is not cryptographic authorship.

## Corpus

The suite loads these files and does not copy their envelopes into a second
vector document:

- `packages/protocol/test-vectors.json`
- `packages/protocol/tm1-test-vectors.json`
- `packages/verification/tm1-authorization-vectors.json`
- `tests/fixtures/rfc0001_regtest_reference.json`

Stored TM0 rows cover valid envelopes, invalid structure, bad UTF-8, an
unknown marker, and the `TM1|` marker rejected as `UNSUPPORTED_VERSION`.
The 80-byte and 81-byte TM0 boundaries are generated by the same rule the
JSON attributes to `packages/protocol/test/vectors.test.ts`, because those
rows store a note rather than an envelope.

Stored TM1 rows cover a valid version `0x01` POST, direct and `OP_PUSHDATA1`
boundaries, the 212-byte maximum, the 213-byte rejection, a non-zero author
byte, canonical errors, version `0x02` as `UNSUPPORTED_VERSION`, and the
reserved event `0x02` under version `0x01` as `UNSUPPORTED_EVENT_TYPE`.
One-byte derivations of that reserved-event script probe other event bytes
and version `0x02` with events `0x02` through `0x05`. They are probes of the
real parser, not new canonical vectors. Version is rejected before event
type, so a version `0x02` envelope is `UNSUPPORTED_VERSION` even when its
event byte is also unknown.

Transaction rows cover one TM1 candidate, a non-zero output value, duplicate
TM1 candidates, a malformed second LOKAD candidate, and a mix of TM0 and TM1.
Normative cardinality is `isTm1CandidateScript`. Application cardinality is
`findMemoCandidates` and `verifyNormalizedTransaction`. The same functions receive the authorization vectors. Raw transaction bytes
are only an adapter that locates scripts and values. Prevout metadata comes
from the vector. A missing prevout entry stays `outputScriptHex: null`; the
adapter does not invent a script.

Those authorization outputs are not canonical two-push envelopes. The
generator in `packages/verification/scripts/generate-authorization-vectors.mjs`
pushes the version, event type, author index and event data separately.
`isTm1CandidateScript` is still true, and `parseTm1Output` returns
`INVALID_FORMAT`. `verifyNormalizedTransaction` therefore returns
`INVALID_TM1` before the author stage. That is baseline behavior. The suite
records it as `fixture-envelope-shape` and still calls
`verifyTm1DesignatedInput` with the vector's declared index, which is the
stage that owns range, P2SH, scriptSig, HASH160 and sighash checks.

To reach those same codes on the application path, the suite keeps the
vector's inputs and replaces only the output with a stored canonical
envelope (`6a04544d4d000401010061`) or with `encodeTm1Post` for author bytes
1, 2 and 255. That composition is labeled as such. It is not a claim that the
original raw output parsed.

The regtest fixture is lab evidence. Its POST output is parsed as a version
`0x01` POST. Its REPLY output is rejected with `UNSUPPORTED_VERSION`. The
experimental harness in `tests/protocol/rfc0001_regtest_reference.test.mjs`
does not import the production parser. It classifies the same REPLY as
`ONE_CANDIDATE` and reads version `0x02`. That harness result is an
expected-v2-rejection difference, not a Core acceptance and not a regression
of the ratified parser.

## Classifications

| Class | Meaning in this suite |
| --- | --- |
| `match` | The production function returns the stored verdict at the stage that function owns. |
| `application-policy` | Normative TM1 count and the TM0/TM1 application verdict differ as described in ratification section 11 item 2. |
| `expected-v2-rejection` | The production parser rejects version `0x02` with `UNSUPPORTED_VERSION`. The experimental harness can still count the LOKAD. |
| `trusted-chronik-gap` | `verifyTm1DesignatedInput` returns `valid: true` for a vector whose stored failure is `cryptographic-signature`. With a canonical two-push envelope, `verifyNormalizedTransaction` then returns `VERIFIED_TM1`. |
| `fixture-envelope-shape` | Authorization vectors store version, event, author and event data as separate pushes. The production parser rejects those outputs as `INVALID_FORMAT` before authorship. The suite does not rewrite them. |

No protected-tree change is classified as an expected protocol change. The
trees are identical to the baseline, so a divergent production verdict fails
the suite instead of being renamed as a regression after the fact.

`invalid-author-input-out-of-range` declares index 1. On its original raw
output, `verifyNormalizedTransaction` stops at `INVALID_FORMAT`.
`verifyTm1DesignatedInput` is called with the declared index and returns
`AUTHOR_INPUT_OUT_OF_RANGE`. The application path reaches that same code only
after the output is replaced with a canonical envelope whose author byte is 1.
Index 255 is produced with `encodeTm1Post`, parsed back as byte 255, and then
rejected against a one-input transaction. Structural acceptance of the byte
is not `VERIFIED_TM1`.
