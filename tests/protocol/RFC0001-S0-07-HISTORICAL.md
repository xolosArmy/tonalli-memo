## Three contracts

TM0 is the text envelope implemented by `decodeMemo` and `validateMemo`.
The marker is exactly `TM0`. A marker of `TM` plus digits, including the
string `TM1`, is `UNSUPPORTED_VERSION`. Any other unexpected marker is
`INVALID_MARKER`. The default maximum is 80 UTF-8 bytes.

TM1 Draft 0.2 is the historical specification in
`docs/protocol/tm1-spec.md` and the wording still present in the
implementation. It defines LOKAD `544d4d00`, version `0x01`, and one active
event, POST `0x01`. The package version and `tm1-test-vectors.json` still
say spec draft `0.2`. Draft 0.2 does not authorize P2SH authorship, and its
candidate rule is the LOKAD prefix.

TM1 Core v1.0 is the contract ratified by the baseline merge. It keeps POST
`0x01` and rejects `REPLY=0x02`. Social version `0x02` stays outside Core.
Ratification section 11 item 2 permits an unrelated `OP_RETURN` beside
exactly one TM1 candidate, and it records that the Tonalli verifier may
also reject a combined TM0 plus TM1 transaction as an
implementation/profile difference. That sentence documents the difference.
It is not itself the later governance act. Section 11 item 7 keeps RFC-0001
outside Core. The Draft 0.2 instruction not to emit production TM1 was
superseded prospectively by that ratification; this suite does not reopen
it and does not activate version `0x02`.

Comment `6529195032` on PR #40, written by `xolosArmy` at
2026-10-30T17:33:45Z, approves the combined profile as an RFC-0001
application policy. S0-07-PROFILE-DECISION is approved. The approval
does not modify the TM1 Core v1.0 contract and does not satisfy S0-07.
The three outcomes, already executed by this suite, are:

- TM0 and TM1 in one transaction: `MULTIPLE_MEMOS`. The application must not select one candidate.
- Two TM1 candidates: `MULTIPLE_MEMOS` under Core.
- One TM1 candidate plus an unrelated `OP_RETURN` that is neither TM0 nor TM1: allowed when the other rules pass.

The comment was left on PR #40 so that HEAD
`19d3b4dd336d497391a036fd4ae6e8f0c2ffe176` and its review receipts stay
put. This file cites that comment. It does not edit the RFC.

`author_input_index` has two different stages. `parseTm1Output` accepts any
byte 0 through 255 inside a well-formed version `0x01` POST. That acceptance
is structural. `verifyTm1DesignatedInput` then checks the index against the
input list, prevout availability, P2PKH script form, scriptSig shape, HASH160,
and sighash `0x41` or `0xc1`. It returns before any signature digest check.
`VERIFIED_TM1` from `verifyNormalizedTransaction` carries
`trustModel: "trusted-chronik"`. It is not cryptographic authorship.

## Canonical P2PKH corpus

`tests/fixtures/rfc0001-canonical-tm1-p2pkh.json` is a synthetic TM1 Core
v1.0 corpus. `tests/protocol/generate-canonical-tm1-fixtures.mjs` builds
the canonical two-push `OP_RETURN` and every other output, then signs with
`ecash-lib` 4.13.0. It does not modify
`packages/verification/scripts/generate-authorization-vectors.mjs`.
`tests/protocol/canonical-tm1-independent-verify.mjs` does not import
`TxBuilder` or `UnsignedTx.sigHashPreimage`. It rebuilds the BIP143
preimage locally and checks Schnorr or ECDSA with the ECC verify
primitives only. The generator refuses a row whose preimage differs from
that checker. The suite runs the generator with `--check` and repeats the
reconstruction, a separate `sha256d` of the stored preimage, and the
signature check.

Every row uses `source: synthetic-fixture` and `chronikValidated: false`.
A `VERIFIED_TM1` result here is `trustModel: trusted-chronik` on a
synthetic normalized transaction. It is not a Chronik response, not a node
validation, and not an on-chain confirmation.

Positive rows are version `0x01` POST, exactly two pushes, LOKAD
`544d4d00`, with author index 0 and nonzero indexes, and sighash `0x41`
and `0xc1`:

| Id | Author | Sighash | Algorithm |
| --- | --- | --- | --- |
| `canonical-schnorr-author0-sighash-41` | 0 | `0x41` | Schnorr |
| `canonical-schnorr-author1-sighash-41` | 1 | `0x41` | Schnorr |
| `canonical-schnorr-author0-sighash-c1` | 0 | `0xc1` | Schnorr |
| `canonical-schnorr-author2-sighash-c1` | 2 | `0xc1` | Schnorr |
| `canonical-ecdsa-author0-sighash-41` | 0 | `0x41` | ECDSA |

ECDSA coverage is the one `0x41` DER fixture above. The independent
checker verifies that signature. The production designated-input function
still does not check the digest; it accepts the two-push scriptSig only
structurally. No other ECDSA sighash is claimed. The private keys are
deterministic insecure test keys inside the generator and are marked never
for funds. The JSON stores public keys only.

Negative rows name the stage that rejects. A digest case is signed first
and mutated afterward, and it still passes the structural stages:

| --- | --- |
| `negative-signature-altered` | Independent `cryptographic-signature`. Production still returns `VERIFIED_TM1` / `trusted-chronik`. |

| `negative-prevout-amount` | Same production gap. The raw transaction is unchanged and the prevout amount used in the preimage is wrong. |

the historical authorization file. That historical file stays unmodified
and remains `fixture-envelope-shape`.

The regtest fixture is lab evidence. Its POST output is parsed as a version

### FALSE-TM0-CLASSIFICATION

`normalizeOpReturnOutput` calls `getStackArray`. That function treats
`OP_RESERVED` as a one-byte stack item, then returns each following data
push. `findTm0Candidates` then keeps every push of at least two bytes that
starts with `54 4d`. The proposed TMM push starts with `544d4d00`, so it is
classified as TM0. `isTm1CandidateScript` does not match, because the byte
after `OP_RETURN` is `OP_RESERVED` rather than a LOKAD data push.
`parseTm1Output` returns `INVALID_MARKER`. Those are different results. The
suite records both and does not change production.

Reproducible positive script, 92 bytes:

```text
6a5031534c5032000453454e44085930c985cca74ff3c3b73c2a8053634bd3c818f50c98e9c530c6090fbd23c9017d000000000027544d4d00020501000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f
```

Observed candidates on that script alone: one TM0 candidate at output 0,
push 2. Its bytes are the 39-byte TMM entry. There is no TM1 candidate.
`verifyNormalizedTransaction` returns `INVALID_MEMO` with `INVALID_FORMAT`.
The same candidate set with author index 255, or with a target byte `0xff`,
returns `INVALID_MEMO` with `INVALID_UTF8`. The verifier status is therefore
not stable across binary targets that are well formed as TMM entries.

Under the current profiles the expected result is narrower than that
observation. An eMPP container is not a TM0 memo and not a TM1 POST.
Social version `0x02` stays inactive. The ordinary two-push control
`two-push-social-v2-inactive` is a TM1 candidate and is rejected with
`UNSUPPORTED_VERSION`. A raw `findTm0Candidates` call also matches a real
TM1 LOKAD, because that push starts with `TM`. `findMemoCandidates` then
excludes outputs already claimed as TM1. The eMPP output is not claimed as
TM1, so the exclusion does not apply and the TMM push survives as TM0.

Consequences for historical compatibility: an eMPP transaction that reached
this verifier would be reported as an invalid TM0 memo, as `MULTIPLE_MEMOS`
when another TM0 or TM1 output is present, or as `NO_MEMO` when the script
exceeds 223 bytes and `getStackArray` drops it. A real TM1 POST beside the
container is hidden by `MULTIPLE_MEMOS`. None of those statuses is a social
tip. Consequences for a future social v2 profile: activation cannot proceed
while this prefix scan treats the TMM push as TM0. A later profile would
have to recognize the eMPP container before that scan, without weakening
the rule that one real TM0 and one real TM1 together are `MULTIPLE_MEMOS`.
This corpus does not implement that dispatch. The behavior stays a
compatibility block until an independent decision. It is not a production
patch.

A canonical ALP SEND plus one 39-byte TMM cannot hit 223 or 224 bytes by
output count alone. Twenty-two SEND outputs produce 219 bytes and still
take the false TM0 path. Twenty-three produce 225 bytes: the independent
reader still describes the SEND and the TMM and flags
`BYTE_BUDGET_EXCEEDED`, while production normalizes the script as malformed
and returns `NO_MEMO`. The exact 223-byte and 224-byte scripts add a
non-protocol push to the 219-byte script. 223 still produces the false TM0
candidate. 224 follows the 225-byte disappearance.

The six recorded axes stay separate. A proposed structural shape can have a
valid container, a structurally valid ALP SEND, and a structurally valid
TMM entry while authorship stays `NOT_DEMONSTRATED`, the atom map stays a
structural output index rather than an attributable transfer, and settlement
stays `PENDING`. Token history is not checked. ALP BURN, MINT, an unknown
action, a truncated SEND, a wrong token id, a reversed or truncated target,
a non-minimal push, and a zero-atom SEND are structural rejects even when
production's only visible result is the false TM0 status.
